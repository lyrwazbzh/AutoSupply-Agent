# 五态池与健康

用户级 Docker 沙箱：预热池认领、Mongo 记 `user→container`、空闲回收；健康失败时 Manager 换容器，Proxy 外层引用不变。熔断中间件在连续失败后暂时拒绝沙箱类工具；Docker 不可用时主 Agent 回退 `LocalShell`。

代码：`src/agent/backends/sandbox_manager.py`、`sandbox_holder.py`、`sandbox_setup.py`、`sandbox_proxy.py`、`custom_opensandbox.py`、`seccomp.json`；中间件 `src/agent/middlewares/sandbox_health.py`、`sandbox_breaker.py`；装配 `src/agent/main_agent.py`；请求租约 `src/api_view/api/chat.py`；后台补池/回收 `src/api_view/web_main.py`。进程入口与维护循环见 `01/01`；主 Agent 中间件栈见 `03/01`。

出现 `get_sandbox(user_id)`，就是 Manager 按优先级拿到容器连接。出现 `SandboxBackendProxy`，就是 Agent / 工具长期持有的稳定句柄。出现 `active_runs` / lease，就是流式请求占用计数，挡住空闲回收。出现 `generation`，就是 Proxy 热替换代次。

---

## 1. 解决什么问题

每个用户的 `/workspace` 要隔离执行；每次对话都 `docker create` 太慢；进程重启后要认回已有容器；健康失败要换容器，但 DeepAgents 在建图时已持有 Backend，外层句柄必须仍可用；沙箱类工具连续失败时要短路，避免拖垮整轮 Agent。

拆成四件事：

| 事 | 谁负责 |
|----|--------|
| 容器何时建、认领、回收、重建 | `SandboxManager` |
| Agent / 工具拿到哪一个句柄、并发如何隔离 | `SandboxBackendProxy` + `sandbox_holder` |
| 请求前探活与热替换 | `SandboxHealthMiddleware` |
| 沙箱工具连续失败时降级 | `SandboxCircuitBreakerMiddleware` |

## 2. 架构 / 数据流

### 2.1 五态与条目

`SandboxState`：`WARM`（预热池空闲）→ `CLAIMED`（已分给用户）→ `CACHED`（已写入 Mongo `sandbox_cache`）；另有 `CREATING`（补池在建计数用）、`DESTROYED`（已移除）。

`SandboxEntry` 挂一条容器：`CustomOpenSandbox`、`user_id`、状态、时间戳、`active_runs`。Manager 内存：`_entries`（container_name → entry）、`_user_map`（user_id → container_name）、`_warm_creating`（补池在途数，防超量）。进程级单例 `sandbox_manager`。

```text
WARM ──认领──→ CLAIMED ──persist──→ CACHED
  ↑                                    │
  │ 补池                          故障/空闲超时
  │                                    ↓
CREATING（计数）                   DESTROYED
  │
  └── 池空时按需 CREATE → CLAIMED → CACHED
```

配置默认：`SANDBOX_WARM_POOL_SIZE=1`，`SANDBOX_IDLE_TIMEOUT_MINUTES=30`，维护间隔 `SANDBOX_MAINTENANCE_INTERVAL_SECONDS=60`，健康检查间隔 `SANDBOX_HEALTH_CHECK_INTERVAL_SECONDS=30`。

### 2.2 请求路径

```text
lifespan（web_main）
  ensure_warm_pool
  后台：cleanup_idle_sandboxes + ensure_warm_pool
  ↓
create_main_agent
  Manager.get_sandbox(user) → CustomOpenSandbox
  包成 SandboxBackendProxy → set_sandbox(Proxy, user)
  CompositeBackend 持有 Proxy；挂 Health / Breaker
  ↓
SSE 一次对话（chat）
  acquire_lease(user)     # active_runs++
  bind_sandbox(user)      # ContextVar ← 注册表里的 Proxy
  ↓
  before_agent：Health 节流 ping → 失败达阈值则 rebuild + replace_backend + on_rebuild
  工具调用：Breaker 只拦沙箱名单；其余直通
  工具经 get_sandbox() 取当前协程绑定的 Proxy
  ↓
  finally：release_lease；reset_sandbox
```

Docker 创建失败时：`LocalShellBackend`，`set_sandbox(None, user)`，Health 无 Manager/backend 视为恒健康。

### 2.3 职责切分

| 角色 | 做什么 |
|------|--------|
| Manager | 五态池、Mongo 映射、lease、空闲回收、`rebuild` |
| `create_secure_sandbox` | 加固 Docker 参数 + 起容器 + 包 `CustomOpenSandbox` |
| Proxy | 外层对象不变，锁内换 `_backend`，`generation++` |
| Holder | 用户→Proxy 注册表 + 请求级 ContextVar，防并发串用户 |
| Health | before_agent 探活；失败则 Manager.rebuild + Proxy.replace_backend |
| Breaker | 沙箱工具三态熔断；MCP/ERP 等不受影响 |
| CustomOpenSandbox | 对已 running 容器的 execute / 文件 API |

## 3. 核心设计与实现

### 3.1 Manager：认领优先级与池

**`ensure_warm_pool`。** 缺口 = 目标池大小 − 当前 WARM 数 − `_warm_creating`；≤0 则返回。锁内抬 `_warm_creating`，锁外 `_create_warm_container`：名 `erp-sandbox-warm-…`，`SandboxConfig(runtimes=[])` 跳过耗时运行时安装；`mkdir` `/workspace` 树与 `/skills`。认领后后台线程再补池。

**`get_sandbox(user_id)` 四级。**

1. 内存已有且 `ping` 健康 → `touch` 返回；不健康 → `_remove_entry`（含 `destroy_container`）
2. `_restore_from_mongodb`：`sandbox_cache` 有记录且 Docker 仍 `running` → 包成 `CustomOpenSandbox` 挂回（**先于认领预热**，避免旧容器变孤儿）
3. `_claim_from_warm_pool`：挑健康 WARM → 标 `CLAIMED`、写 `_user_map`、`_persist_to_mongodb`（状态变 `CACHED`）、线程补池
4. `_create_for_user`：名 `erp-sandbox-{safe_user}-…`；锁内外二次检查防双建，落败方 `destroy_container`

**Mongo。** `sandbox_cache` 按 `user_id` upsert `entry.to_dict()`。恢复时容器未 running 或不存在则删缓存。持久化失败只打 warning，认领仍成功。

**租约与回收。** `acquire_lease` / `release_lease` 增减 `active_runs`（下限 0）。`cleanup_idle_sandboxes`：仅 `CLAIMED`/`CACHED`，且 `active_runs==0`，且闲置超超时 → 销毁并清 Mongo / `_user_map`。`rebuild`：记下旧 `active_runs`，拆旧建新，计数迁到新 entry。`touch` 供 Health 刷新 `last_active_at`。

```text
get_sandbox(user)
  → 内存健康？→ 返回
  → Mongo + Docker running？→ 恢复
  → 认领 WARM？→ persist + 补池
  → 新建（竞态守卫）
```

### 3.2 创建加固：`sandbox_setup` + seccomp

**`SandboxConfig`。** 镜像 / 容器名 / `work_dir`；`read_only`、内存 `512m`、CPU `1.0`、`network_mode`（默认 `bridge`）、tmpfs、`drop_all_caps`、`use_seccomp`；`runtimes`（默认 `["python"]`，预热传空列表）。

**`create_secure_sandbox`。**

1. 同名容器先 stop/remove  
2. `host_config`：只读根、内存/CPU、`pids_limit=256`；tmpfs 挂 `/tmp`、`/workspace`（256m）、`/skills`（128m，Skills 同步可写）  
3. `cap_drop ALL`，加最小 `CHOWN`/`SETUID`/`SETGID`/`DAC_OVERRIDE`；`seccomp=<路径>` + `no-new-privileges`  
4. 环境：`PIP_TARGET` / `PYTHONPATH` → `/workspace/python-packages`（根只读时依赖装工作区）  
5. `containers.run(..., sleep infinity)`；失败回退无加固基础 `run`  
6. 包成 `CustomOpenSandbox`，按需 `_init_runtimes`

**`seccomp.json`。** `defaultAction` 为 `SCMP_ACT_ERRNO`（未列出的 syscall 失败）。与只读根、cap-drop、pids-limit 叠用，收紧容器内内核能力面。

**`create_and_setup_sandbox`。** 按 user 创建后 mkdir，再 `_sync_project_files`（skills、requirements、mcp_server、tools、schema；不拷密钥）。主链路更多走 Manager + 中间件灌技能。

### 3.3 Proxy：稳定句柄与热替换

DeepAgents 建图时持有 Backend；故障后若换新 `CustomOpenSandbox` 实例，`CompositeBackend` 与工具仍握旧对象。`SandboxBackendProxy` 自身是 `BaseSandbox`，外层身份不变。

**`replace_backend(new)`。** 锁内换 `_backend`、`_generation += 1`；对旧 backend 尽力 `destroy()`（断 SDK；删容器归 Manager）。

**委托。** `execute` / 上传下载走当前层；`ping` 优先底层 `ping`，否则 `echo ok`；`__getattr__` 透传 `write_file` 等扩展方法。调用方读 `backend` 属性时得到快照，长期缓存该快照会错过热替换——工具应经 Proxy / `get_sandbox()`。

### 3.4 Holder：注册表 + ContextVar

多路 SSE 并发时，模块级「当前沙箱」全局会串用户。Holder 维护：

- `_sandboxes_by_user`：`set_sandbox(Proxy, user_id)` 在装配时写入  
- `_request_sandbox` ContextVar：`bind_sandbox` 在请求开始把该用户 Proxy 写入当前协程，`reset_sandbox` 在 finally 复位  

`get_sandbox()`：先 ContextVar，再按 user 查注册表（默认 `default_user`）。`has_sandbox`：非空且 `ping()` 成功。

```text
Manager.get_sandbox → Proxy → set_sandbox(Proxy, user)
  请求：bind → 工具 get_sandbox() → finally reset
```

### 3.5 CustomOpenSandbox：连已有容器

连已存在且 running 的容器；高层文件 API 落到 `execute` 或 tar/base64。

**`execute`。** `bash -c "cd work_dir && …"`，stdout/stderr 合并，超 100KB 截断；未连接返回 `exit_code=-1`。

**文件。** 读：`read_file` / `read_file_bytes`。写：`write_file`（mkdir 父目录，base64 落盘）。另有 `list_dir`、`file_exists`、`mkdir`/`rm`/`cp`/`mv`、`glob`/`grep`，以及 `pip_install`、`python_exec` 等。

**生命周期。** `ping`：`reload` 后看 running。`destroy`：只断 SDK。`destroy_container`：stop + remove，给 Manager 回收。

### 3.6 Health：请求前探活与重建

每次 Agent 跑前验证用户沙箱；故障时换容器并保持 Proxy 引用。

**构造。** `sandbox_manager`、`sandbox_backend`（通常 Proxy）、`user_id`、`on_rebuild`；`check_interval` 默认 30s；`failure_threshold` 默认 1。无 Manager 或无 backend（LocalShell）→ 视为健康。

**入口。** `before_agent` 同步检查；`abefore_agent` 用 `to_thread`，避免堵 SSE 事件循环。

**`_check_and_recover`。**

1. 健康且未到检查间隔 → 跳过  
2. ping 成功 → `touch`、清失败计数  
3. 失败累加，达阈值 → `_rebuild_sandbox`：`Manager.rebuild` → `Proxy.replace_backend` → 可选 `on_rebuild`（技能再灌装等）→ 再 ping；失败抛 `RuntimeError`（阻断把请求交给失效容器）

### 3.7 Breaker：沙箱工具三态熔断

对沙箱类工具做三态熔断；MCP / ERP 等照常走。名单：`execute` / `run_code` / `run_python` / `shell` / `bash`。

| 态 | 行为 |
|----|------|
| CLOSED | 调 handler；成功清零计数；失败累加 |
| OPEN | 直接返回错误 `ToolMessage`（status=error），不调 handler |
| HALF_OPEN | OPEN 满 `recovery_timeout`（默认 60s）后允许试探；成功 → CLOSED |

连续失败 ≥ `failure_threshold`（默认 3）→ OPEN。异常记失败并返回错误消息（不抛出图外），Agent 可改用其他工具。

```text
before_agent
  Health：节流 ping → 失败则 rebuild + replace_backend + on_rebuild

工具调用
  Breaker：非沙箱 → handler
         OPEN → 降级 ToolMessage
         CLOSED / HALF_OPEN → handler → 成功关闸 / 失败累计
```

## 4. 关键设计取舍

| 取舍 | 现行做法 |
|------|----------|
| 句柄 vs 生命周期 | Manager 管 create/destroy；Proxy 管引用稳定；Holder 管并发绑定 |
| 探活 vs 回收 | 请求路径 Health 做 ping/重建；后台循环做空闲回收与补池 |
| 恢复顺序 | 先 Mongo 恢复再认领 WARM，避免旧容器孤儿 |
| 预热成本 | `runtimes=[]`，依赖按需装到 `/workspace/python-packages` |
| Docker 不可用 | 主 Agent 回退 LocalShell；Health 跳过 |
| 停机 | 不销毁已认领容器；靠 `sandbox_cache` 重启后连接 |

---

## 5. 工程边界

| 主题 | 现行行为 |
|------|----------|
| 单进程状态 | Manager、Holder 注册表、lease 计数在本进程；多 worker 各有一份池与映射，跨进程靠 Docker + Mongo |
| 工具取沙箱 | 经 Proxy / `get_sandbox()`；长期缓存底层 Docker 对象会错过 `replace_backend` |
| lease 与五态 | `active_runs` 是请求级占用；五态是容器生命周期；有 lease 时 `cleanup_idle` 跳过 |
| generation | Proxy 热替换代次；技能同步 / 恢复可据此清缓存 |
| Health vs Breaker | Health：容器死了换新，Proxy 仍可用。Breaker：沙箱工具连续炸，先短路再试探 |
| 加固回退 | `create_secure_sandbox` 失败可走无加固 `run`；生产依赖 Docker 可用与权限 |

## 6. 面试记忆点

**认领为什么能快？**  
池里已有 WARM 容器，认领改状态与映射并 persist，少走完整 create。

**lease 和五态？**  
lease（`active_runs`）是请求级占用；五态是容器生命周期。有 lease 时不做空闲回收。

**Health 和 Breaker 分工？**  
Health：容器死了换新，Proxy 仍可用。Breaker：沙箱工具连续炸，先短路再试探。

**为什么必须有 Proxy？**  
建图时 CompositeBackend / 工具已持有 Backend 对象；热替换只换 Proxy 内部指针，外层引用与 session 图状态保留。

**收束。** 沙箱是本地工具和 Skills 脚本的执行面；HTTP 借 lease，create/destroy 在 Manager，句柄稳定靠 Proxy，探活在 Health，降级在 Breaker。复习时先对节 2 请求路径，再对 3.1 / 3.3 / 3.6 三条主路径。
