# 加载规格与委派门禁

四个子 Agent 用 YAML 声明角色：`name`、`description`、`system_prompt`、`tools`，以及 `context_protocol`（交接字段、`output_format`）。加载器把 YAML 收成可交给 `create_deep_agent(subagents=...)` 的规格。主 Agent 调框架工具 `task` 时，门禁做注册表校验、交接抽取、并行记账、超时包装与回流核验；start/end 事件进请求级缓冲，由 SSE 推出。

代码：`src/agent/subagents/loader.py`、`task_dispatch.py`、`dispatch_events.py`，`configs/*.yaml`；中间件 `src/agent/middlewares/delegation_gate.py`（`TaskDispatchMiddleware`）；装配 `src/agent/main_agent.py`；事件消费见 `src/api_view/api/chat.py`。主提示与委派条件见 `memory/prompts.py`、`memory/AGENTS.md`（字段明细以四份 YAML 为准）。Harness 评审见 `03/01`。

出现 `task(subagent_type, description)`，就是一次委派。出现 `<delegation-context>`，就是校验通过后注入到 description 前的键值块。

---

## 1. 解决什么问题

齐套分析和催交订单：上下文不同，工具子集不同。各自隔离跑，结构化回流，前端能画并行条带。

| 层 | 职责 |
|----|------|
| YAML `configs/*.yaml` | 角色、工具名、交接/回流契约、`interrupt_on` |
| `loader` | 校验 → 绑工具对象 → 子提示契约 + 主提示委派协议 |
| `TaskDispatchService` / `Gate` | 这一次 `task` 能不能跑、回来合不合格 |
| `TaskDispatchMiddleware` | 认出 `task`、改 description、套超时、变成 ToolMessage |
| `dispatch_events` | 请求级 start/end 缓冲 → SSE / 落库 |

缺省：description 至少 24 字，并行最多 4，超时 180 秒。父 messages 不传入子 Agent；子 YAML 的 `tools` 不含 `task`。

---

## 2. 架构 / 数据流

```text
configs/*.yaml
        │
        ▼
load_subagent_configs（必填 name/description/system_prompt/tools）
        │
        ▼
resolve_subagent_tools（精确名 → name_ 前缀 → 子串）
get_delegation_context_prompt → 拼进主系统提示
        │
        ▼
create_deep_agent(subagents=...)
        │
        ▼
主 Agent 调 task
        │
        ▼
TaskDispatchMiddleware
  → Gate.before_call（validate / enrich / begin）
  → 超时包装执行子 Agent
  → Gate.after_result（verify / replace / end）
        │
        ▼
publish_dispatch_event → ContextVar 缓冲
        │
        ▼
chat.py drain → SSE agent_dispatch → save_dispatch_trace
```

四个 `name`（即 `subagent_type`）：

| name | 文件 | 侧重 |
|------|------|------|
| `supply-planning-analyst` | `procurement_analyst.yaml` | 计划 / 缺料 / BOM |
| `strategic-sourcing` | `strategic_sourcing.yaml` | RFQ / AVL / 定点 |
| `delivery-collaboration` | `procurement_order.yaml` | 订单 / 交付 / ASN |
| `supplier-quality-risk` | `supplier_quality_risk.yaml` | PPAP / 质量 / 供应风险 |

Harness 的 `task_types`（analysis / order / …）是评审条文分类；这里四个 `name` 是 `task` 的委派角色。SSE `token.source` 按子图名子串归 analyst / order / main，与这四个名字是两套标签。

## 3. 核心设计与实现

### 3.1 加载器：`loader.py`

**`load_subagent_configs`。** 扫 `configs/*.yaml`；必填四键且非空才收录；读失败或缺字段跳过并打日志。空文件算无效配置。

**`resolve_subagent_tools`。** 对每个配置的工具模式串，在 `all_tools` 上按 **精确名 → `pattern_` 前缀 → 子串** 匹配（前缀边界降低 `"order"` 误中 `reorder_*` 的风险）。拼出规格：`name`、`description`、系统提示（可再拼输出契约）、工具对象列表；YAML 有 `interrupt_on` 则解析进规格。无匹配打 warning。

**输出契约。** `output_format` 可在顶层或 `context_protocol` 内。有 `sections` 字符串列表则合法；`build_output_contract_prompt` 生成「必须含哪些 section」段落，接到子 Agent `system_prompt` 后面。

**主侧委派协议。** `get_delegation_context_prompt`：按各 YAML 的 `input_context` 生成「委派给某某时 description 要写哪些字段」段落，拼进主 Agent 系统提示。无协议则空串。

```text
YAML → 校验 → configs
configs + all_tools → 绑工具 + 契约 → subagents
configs → 委派协议文案 → 主提示词
```

### 3.2 调度服务与门禁：`task_dispatch.py`

「何时该派」仍在主提示词（可并行 / 上下文隔离 / 调用链深）。本模块管工程侧：注册表、交接、并发、事件、回流核验。

**`SubAgentRegistry`。** `name → 配置`；可查某角色的 `input_context` 字段列表、`output_format.sections`。

**交接字段。** 从 description 解析 `字段名: 值`（含冒号变体）。占位值（未知、待定、n/a、xxx、tbd…）算无效。`user_id` / `username` / `user_preferences` 可从 `ProcurementContext` 自动填；其余必填必须在 description 里写真实值。description 里若写了身份字段，服务端仍以 Context 身份为准。

**`TaskDispatchService.validate`。** 缺 type、未知角色、空/过短 description、并发已满、必填缺失或值无效 → 拒绝并带原因。通过则 `enrich_description`：前面加 `<delegation-context>`（type、已填字段、必填列表），再接原文。`begin` / `end` 发 start/end 事件（含 `elapsed_ms`、`active_parallel` 等）。

**回流核验 `verify_output_contract`。** 每个声明的 section 要在正文里找到且非空。落在 `evidence` / `data_table` / `charts` / `comparison` / `risk_assessment` / `conclusions` 的 section，还要有表格、路径或工具名引用。

**`TaskDispatchGate`。**

| 阶段 | 决策 |
|------|------|
| `before_call` | 失败 `reject`；成功 `allow` + 改写后的 description，并 `begin` |
| `after_result` | 工具已是 error → `end(error)`；核验不过 → `replace` 成「委派结果不合格」并 `end(verification_failed)`；过则 `end(completed)` |
| `on_timeout` | `replace` 超时文案并 end |

```text
task 调用
  → validate（角色 / 字段 / 并发）
  → enrich + begin
  → 子 Agent 跑（中间件套超时）
  → verify sections[+证据]
  → allow 或 replace → end 事件
```

### 3.3 中间件：`delegation_gate.py`

主 Agent 上拦 DeepAgents `task` 的那一层（别名 `DelegationGateMiddleware`）。校验/注入/核验委托 Gate/Service；本文件挂 LangChain 工具链并用超时包住真正执行。`tools = []`，不往工具袋加工具。默认最短 description 24 字、并行最多 4、超时 180 秒。

**调用前。** 工具名不是 `task`：直接放行。是 `task`：走 `before_call`。拒绝 → 立刻 `[委派被拒绝] …`，子 Agent 不跑；通过 → 把 `description` 换成 enriched 再进 handler。

**执行。** 同步：`ThreadPoolExecutor` + `future.result(timeout)`。异步（chat `astream`）：`asyncio.wait_for`。超时 → `[委派超时] …`；其它异常先 `end(error)` 再抛出。

**回流。** 结果不是 `ToolMessage`（如 `Command`）：记 completed，原样返回，不做 sections 核验。是 `ToolMessage`：走 `after_result`——自身 error 原样带回；缺 section 或证据不够 → 换成 `[委派结果不合格] …`；通过 → 原文回主 Agent。

### 3.4 请求级事件：`dispatch_events.py`

用 `ContextVar`（`erp_agent_dispatch_events`）挂本请求私有列表，与 `bind_runtime` / `bind_sandbox` 并列。图按 `user_id` 缓存，事件列表跟这一次 SSE 同生共死。

| API | 行为 |
|-----|------|
| `bind` | 开流后绑空列表 |
| `publish` | 已绑定则 append 拷贝；未绑定则丢弃 |
| `drain` | 取出并清空；chat 步进推 SSE `agent_dispatch`、补 timestamp、可落库 |
| `reset` | finally 复位 |
| `overlapping_dispatch_pairs` | 看 end 事件起止时间相交的 call_id 对；单测验真并行，生产路径不调 |

### 3.5 四份 YAML 规格

声明式角色：`name` = `task(subagent_type=...)`；`tools` 经 loader 绑对象；`context_protocol` 管交接与回流；写风险工具再配 `interrupt_on`。

#### `supply-planning-analyst`（`procurement_analyst.yaml`）

计划与齐套。触发面：MRP、缺料、齐套、生产计划、停线、BOM、工程变更。工具偏读：供应商/物料/库存/订单查询 + 项目 BOM / 工程变更 / MRP / 齐套 / 停线 + `generate_chart`、`web_search`。无 `interrupt_on`。

| 面 | 内容 |
|----|------|
| 交接必填 | `user_id`、`username`、`task_objective` |
| 交接可选 | `data_scope`、`user_preferences`、`prior_findings` |
| 回流 sections | `summary` → `data_table` → `charts` → `conclusions` → `recommendations` |

提示词要点：明确目标 → MCP 采数 → 整理 → 出图（尊重图表偏好）→ 结构化报告；建议标工程/质量放行约束。

#### `strategic-sourcing`（`strategic_sourcing.yaml`）

寻源与定点。工具：物料/AVL、报价对比、供应商质量/交付/PPAP，以及写操作 `rfq_create`、`sourcing_nominate`。

| 面 | 内容 |
|----|------|
| 交接必填 | `program_code`、`material_code` |
| 交接可选 | `demand_context`（用量、日期、工厂等） |
| 回流 sections | `summary`、`comparison`、`recommendation`、`risks`、`approval_needed` |
| interrupt_on | `rfq_create`、`sourcing_nominate`：approve / reject |

定点须依据真实报价、AVL、PPAP、质量、交付、产能；非 AVL / PPAP 未放行 / 质量未闭环不得直接当量产供货。

#### `delivery-collaboration`（`procurement_order.yaml`）

交付协同（文件名 order，角色名 delivery）。触发：交付、延期、催交、ASN、订单、交期。工具：订单建改查与状态、`request_order_info`、交付计划/ASN/绩效、物料需求与停线/质量查询。

| 面 | 内容 |
|----|------|
| 交接必填 | `user_id`、`username`、`task_objective` |
| 交接可选 | `order_context`、`extracted_data`、`user_preferences` |
| 回流 sections | `operation_type`、`order_summary`、`status`、`approval_needed`、`next_steps` |
| interrupt_on | `order_create`/`order_update`：approve/reject/edit；`order_update_status`：approve/reject |

创建：合并已提取字段 → 校验订单号与明细 → 缺则 `request_order_info` → 再 `order_create`（会中断审批）。

#### `supplier-quality-risk`（`supplier_quality_risk.yaml`）

供应商质量与风险。工具：供应商/质量/PPAP/交付、AVL 与替代料、停线与供应风险、MRP 缺料、`generate_chart`。无 `interrupt_on`。

| 面 | 内容 |
|----|------|
| 交接 | `supplier_code`、`material_code`、`plant_code` 均为可选（按需写入） |
| 回流 sections | `summary`、`evidence`、`risk_assessment`、`containment_actions` |

风险等级与处置须有数据证据；放行缺失时只建议遏制/整改/复验或升级，不承诺量产可用。

### 3.6 主提示中的委派约定（摘要）

`MAIN_SYSTEM_PROMPT` 与 `AGENTS.md` 约定：`task` 在可并行、上下文隔离、调用链深任一成立时用；四个 `subagent_type` 与 YAML `name` 一致；description 按英文字段名写键值行；身份三类可由服务端注入；禁止占位值。字段明细以 §3.5 为准，不在提示词里另维护一份长表。装配时 `get_delegation_context_prompt` 再按 YAML 生成角色级字段清单拼进主提示。记忆 HOT/WARM/COLD 与 `read_memory` 见 **07**。

## 4. 关键设计取舍

| 取舍 | 现行做法 |
|------|----------|
| 规格形态 | YAML 裁工具子集与契约；改 `input_context` / `sections` 即改校验与核验 |
| 交接 | 键值进 `<delegation-context>`；身份字段服务端填 |
| 回流 | sections 齐全 + 证据类标题要有表/路径/工具引用 |
| 并行 | 上限 4，保护沙箱与 ERP；超时 180s 由中间件包装执行 |
| 观测 | 事件走 ContextVar，SSE 与落库同一批 start/end |

---

## 5. 工程边界

| 主题 | 现行行为 |
|------|----------|
| 工具 pattern | 启动时无匹配打 warning；精确 > 前缀 > 子串 |
| 占位值 | `待定` / `TBD` / `n/a` 等会被拒，子 Agent 不跑 |
| 超时与前端 | 超时已返回错误后，线程池里的 handler 可能仍在跑 |
| Command 回流 | 非 ToolMessage 不走 sections 核验，直接 completed |
| SSE 文案 | 并行条带与标签以 `chat.py` 为准；end 带 `elapsed_ms` |
| 角色 vs 评审类型 | 四个委派 `name` ≠ Harness `task_types` ≠ SSE `token.source` 三分法 |

## 6. 面试记忆点

**主 Agent 怎么选角色？**  
读各 YAML `description`，`task` 带对应 `subagent_type`。

**门禁和加载器各管什么？**  
加载器：YAML → 可运行规格 + 主/子提示契约。门禁：这一次 `task` 能不能跑、回来合不合格。中间件：认出 `task`、改 description、套超时。

**同步和异步各走哪条？**  
`wrap_tool_call`：线程池 `future.result(timeout)`。`awrap_tool_call`：`asyncio.wait_for`。chat 流式走异步。

**前端并行条带从哪来？**  
SSE `agent_dispatch` + Mongo `dispatch_traces`；时间是否交叉看缓冲里 start/end（测试用 `overlapping_dispatch_pairs`）。

**收束。** 加载把 YAML 变成可运行 SubAgent；Service/Gate 把一次 `task` 变成可拒绝、可超时、可核验的调用；缓冲把 start/end 交给本轮 SSE。复习时先对节 2 总流，再对 3.2 / 3.3 生命周期，最后 3.5 四角色表。
